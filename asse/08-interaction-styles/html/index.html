Designed for clients to send database queries and servers to perform (potentially long-running) queries and return (potentially large) data sets.

Client and server need to synchronize on data manipulation concepts for success

-“Traditional Client/Server”: Server takes query and returns result

-“Mobile Object”: Server moves complete database + query engine to client

-Hybrid Style: Clients make multiple queries, iteratively reducing the dataset

Interesting field that currently evolves dynamically due to large-scale (linked) data sets.

Remote Procedure Calls

RPC Core Idea: Achieve Location Transparency!

-Caller of a procedure may remain (largely) oblivious to whether a procedure is implemented locally or remotely

-Often, we still distinguish remote calls from local calls (e.g., since they have very different QoS)

RPCs are a form of inter-process communication

-The different processes have different address spaces

-They may be physically located on the same host or on different hosts

RPC terminology

-Client calls Client Stub with parameters

-Client Stub marshalls parameters

-Client OS sends message (function signature + parameters) to Server OS

-Server OS routes to Server Stub

-Server Stub unmarshalls parameters and calls server procedure

https://www.computer.org/profiles/per-hansen

Common ORB Architecture (CORBA)

Benefits: Level playing field

-Single system model, independent from language and OS

-High (performance) tuning ability for end users

-Highly performant binary protocol

Drawbacks: Complexity and Ambiguity

-Too much location transparency

-Complex specification with ambiguities

-This led to poor (unstable, hard-to-use) concrete implementations

-Huge practical problem: Firewalls

-Some implementations of CORBA required multiple ports to work

-Required custom firewall configurations (today: CORBA-friendly firewalls through General Inter-Orb Protocol; GIOP)

Objects in the same address space treated equal to objects on physically remote machines

Is this a good idea? Why? Why not?

It implies that each request is as complex as the most complex class of requests!

Yes, this really was a huge problem!

From WS-* to CRUD-over-HTTP (CoH)

WS-* uses HTTP as a transport protocol

-SOAP uses only POST and specifies the actual operation in the SOAP message

-Twitter used POST as a broad catch-all and specifies the actual operation in the URI

-In this way, these applications remain outside of the Web

CRUD-over-HTTP uses HTTP as an application protocol

-In doing so, CoH adopts what we refer to as a resource-orientated architecture, or ROA

-Remember from REST’s Uniform Interface?

-URIs are the nouns of your application – all resources that you want to talk about

-Methods from the Uniform Interface are the verbs of your application – they specify how to interact with resources

C. Pautasso, O. Zimmermann, and F. Leymann: RESTful Web Services vs. “Big” Web Services. Making the Right Architectural Decision, 2008

J. Webber, S. Parastatidis, I. Robinson: REST in Practice, 2010

This is perfectly fine if you don‘t want to use the benefits of HTTP‘s uniform interface.

But you should decide consciously!

Create with HTTP POST: Not idempotent, not safe.

Read with HTTP GET: Idempotent and safe.

Update with HTTP PUT: Idempotent, not safe.

Delete with HTTP DELETE: Idempotent, not safe.

And make sure to use the HTTP response codes as intended…

-Induced contract: Changes are pushed to these Hubs, i.e., subscribers may subscribe there

-Intermediaries according to REST’s layered architecture (e.g., Google, Superfeedr)

Subscribers discover Hubs and subscribe to get notifications about relevant content

W3C WebSub Subscription Flow

1.Client retrieves content from an HTTP resource (i.e., the publisher). That resource contains information about a WebSub hub

1.Client starts a Web server locally and POSTs a subscription request to the hub with that server’s callback URI

1.Hub sends a verification request to check subscription request authenticity

1.Hub adds callback URI to its internal list of subscribed clients

1.Publisher updates Hub with new data

1.Hub uses subscriber server’s callback URI to POST updates to it

Sounds like a complicated version of MQTT – why all of this?

-Distributed publish-subscribe on the open Web, at Web scale

-Discovery is decentralized

-Publishing is decentralized

-Hub-provisioning is decentralized

-Discovery and subscriptions happen at run time! This means that we can run-time load balance without recompiling anything!!

No coincidence that this comes out of IndieWeb

Look! The Hub is discovered in-band at run time!!
